Bug 29727: Desktop- DMS- seřazení sloupce Verze se nechová jak má


Shrnutí pro Peťu (CZ)

  Co je za bug?

  Řazení v DMS nefunguje správně — sestupné řazení u VŠECH sloupců (nejen Verze), protože FileComparer při řazení čte zastaralé hodnoty.

  Proč to vzniklo?

  Monika v dubnu 2025 (commit 2fe896526 — "vraceci slozka se radi nahoru") přepsala logiku řazení. Původní kód (David Šeda, 2022) předával směr
  a název sloupce přímo do compareru. Monika to nahradila statickými poli, které se nastavují v eventu SortColumnsChanged — ten ale spouští až
  PO dokončení řazení. Takže comparer při řazení čte hodnoty z předchozího kliknutí.

  Proč si toho nikdo nevšiml?

  - První kliknutí (vzestupně): comparer nemá žádný název sloupce → vrací 0 pro všechno → zachová se původní pořadí → vypadá to správně náhodou
  - Druhé kliknutí (sestupně): comparer teď má správný sloupec, ale směr je stále "vzestupně" z předchozího kliknutí → seřadí vzestupně místo
  sestupně
  - Uživatelé typicky řadí podle názvu vzestupně a jiné sloupce/směry skoro netestují

  Fix (3 změny)

  1. XAML: SortColumnsChanged → SortColumnsChanging (spouští se PŘED řazením)
  2. Code-behind: handler čte z e.AddedItems místo z SortColumnDescriptions
  3. FileComparer: odstraněn řádek, který přepisoval správnou hodnotu od Syncfusion zastaralou statickou hodnotou

Bulk ToDo Update Feature — API Summary

  Endpoint

  PUT /api/todolist/ukoly/bulk

  Accepts a JSON body with:
  - ukolIds — list of ToDo IDs to update
  - kStav — (optional) new state ID
  - deadline — (optional) new deadline date
  - stitkyPridat — (optional) list of tag IDs to add
  - stitkyOdebrat — (optional) list of tag IDs to remove

  Only applies changes that are actually different per ToDo. Returns updatedCount and failedTodos (locked ToDos are skipped with a reason).

  ---
  Handler Logic (BulkUpdateToDosHandler.Handle)

  1. Validates request (non-empty IDs, deadline not in the past)
  2. Pre-loads tag names and state names for history/notifications
  3. Loads all requested ToDos with their tag bindings and creator navigation
  4. Iterates each ToDo:
    - Locked → skipped, added to failedTodos
    - Stav → if different from current, updates + writes history record
    - Deadline → if different, updates + writes history + schedules/reschedules deadline reminder via TodoEmailHelper
    - Tags to add → skips already assigned, creates ToDoUkolyStitkyVazby + history
    - Tags to remove → skips if not assigned, removes binding + history
    - Only counts as changed if at least one field was actually modified
  5. Saves all changes in one SaveChanges() call
  6. Sends notifications — one email per ToDo per affected user (responsible users + creator if not already included)

  Email Notification Flow

  Handler.SendNotifications()
    → Resolves UzelDTO (stavba context for the email)
    → Gets "Přejít na úkol" link
    → Gets recipients: GetOdpovedne() + creator
    → For each recipient:
        → Creates ToDoBulkUpdatedNotificationModel
        → Factory renders Razor template → EmailMessage
        → EmailMessage.Check() verifies user has NotifikaceMail=true + valid email
        → EmailService.Send() → HTTP POST to Azure Email Gate Service
            → Gate service queues → SmtpClient sends via configured SMTP

  The code checks if polozka.Mereni is null on line 395, but it already accesses it on line 393 with .Any(). If any položka under SD "zemní práce" has Mereni == null, it crashes on line 393
  with a NullReferenceException before the null check ever runs.

  Why you don't see the exception: The call chain is:
  1. ExpandCollapse (line 634, async Task)
  2. → calls LoadDataPolozka (line 660)
  3. → NullReferenceException thrown on line 393

  Because ExpandCollapse is async Task and is likely called without await or via a fire-and-forget event handler, the exception gets swallowed by the Task — it never bubbles up to the UI, no
  error dialog appears, the app just silently fails and the grid stops responding (looks like a crash/freeze).

  Proposed Fix

  Move the null check before the .Any() call, and change return to continue (so one bad položka doesn't skip all remaining ones):

  foreach (MereniUzelDC polozka in polozky)
  {
      if (polozka.Mereni == null)
      {
          continue;
      }

      bool uzamceno = polozka.Mereni.Any(p => p.Uzamceno);
      // ... rest stays the same

  CHANGED:
  - Null check moved from line 395 to before line 393
  - return → continue (skip this one položka, don't abort the entire loop)

  INTENTIONALLY UNCHANGED:
  - Everything else in the method stays as-is — the .Any() call, the data mapping, the ZBV logic — none of it is affected

  Root Cause

  The DMS grid has two mechanisms for showing the ".." back arrow:
  1. UnBoundRow at position "Top" (row index 1) — the "proper" back arrow at the top
  2. Data row from FolderContent — the actual ".." item in the data source

  The CollapseNavUpRow method is supposed to hide the data row (since the UnBoundRow handles it). But it only checks e.RowIndex == 2, assuming ".."
  is always the first data row. When the grid is sorted in descending order, ".." ends up at the BOTTOM of the list, and CollapseNavUpRow doesn't
  catch it.

  FILE: Proconom\eConoM\Widgety\Dokumenty\DokumentyWidgetControl.xaml.cs
  METHOD: CollapseNavUpRow
  LINE: 6009

  Current code:
  private void CollapseNavUpRow(SfDataGrid dataGrid, QueryRowHeightEventArgs e)
  {
      if (dataGrid is null)
          return;
      DFileDC navUpItem = GetNavUpItem(dataGrid);
      DFileDC viewedNavUpItem = GetViewedNavUpItem(dataGrid);
      bool noNavUpItem = navUpItem is null && viewedNavUpItem is null;
      if (e.RowIndex == 1 && noNavUpItem)
      {
          CollapseRow(e);
          return;
      }
      bool navUpItemIsFilteredOut = navUpItem is null || viewedNavUpItem is null;
      if (e.RowIndex == 2 && !navUpItemIsFilteredOut)  // ← BUG: only checks row 2
      {
          CollapseRow(e);
          return;
      }
  }

  Proposed Fix

  Replace the hardcoded e.RowIndex == 2 check with logic that identifies the ".." row at any position:

  private void CollapseNavUpRow(SfDataGrid dataGrid, QueryRowHeightEventArgs e)
  {
      if (dataGrid is null)
          return;
      DFileDC navUpItem = GetNavUpItem(dataGrid);

      // Collapse UnBoundRow when no ".." item in source
      if (e.RowIndex == 1 && navUpItem is null)
      {
          CollapseRow(e);
          return;
      }

      // Collapse the ".." data row wherever it appears (could be sorted to any position)
      if (navUpItem is not null && e.RowIndex >= 2 && !dataGrid.IsUnBoundRow(e.RowIndex))
      {
          object record = dataGrid.GetRecordAtRowIndex(e.RowIndex);
          if (record is DFileDC file && file.Nazev == "..")
          {
              CollapseRow(e);
              return;
          }
      }
  }

  Key changes:
  - Instead of only checking row index 2, checks ALL data rows (e.RowIndex >= 2)
  - Uses GetRecordAtRowIndex (already used elsewhere in this file, e.g., line 1986) to identify the actual data at each row
  - Collapses the row only if it contains the ".." item
  - Simplified UnBoundRow check: only depends on navUpItem (from raw ItemsSource), not viewedNavUpItem

  INTENTIONALLY UNCHANGED:
  - GetNavUpItem / GetViewedNavUpItem methods — still useful for the UnBoundRow data population in LvDokumentySlozky_QueryUnboundRowInfo
  - AddReturn() logic — the ".." item still needs to exist in FolderContent for navigation to work
  - FileComparer — the * direction logic there is correct for keeping folders/".." pinned when the grid handles sort reversal; the real issue is the
  collapse logic

  ---
  Hierarchy

  SStavby (stavba)
    └── RObjekty (stavební objekt)
          └── RSd (stavební díl — the section)
                └── RPol (položka — budget line item)
                      └── SSdPol (měření — one measurement record, date + quantity)
                            └── KZbvNavigation (ZBV — change order header)
                                  └── ZbvPol (položka ZBV — allowed quantity for RPol under this ZBV)

  ---
  Key distinction inside SSdPol

  A measurement (SSdPol) can be either:
  - SOD measurement — KZbv == null — measures progress against the original contract
  - ZBV measurement — KZbv != null — measures progress against a specific change order

  This is why SetPol splits them:
  // SOD measurements only
  pol.SSdPol.Where(x => x.KZbv == null)

  // ZBV measurements only — handled separately in SetSSDPolZeZBV
  pol.SSdPol.Where(x => x.KZbvNavigation != null && !x.KZbvNavigation.Stav)

  So SSdPol is not a type of položka — it is a measurement event. RPol and ZbvPol are the two types of položky.

  FILE: TiskReportApi/Helpers/ReportMereniPolozekZaObdobiExcel.cs
  METHOD: GetData()

  protected override async Task GetData()
  {
      SStavby stav = await _ctx.SStavby
          .AsNoTracking()
          .AsSplitQuery()
          .Where(s => s.XId == req.StavbaId)

          .Include(s => s.SStavbyNastaveni)

          // First path — loads KMjNavigation (unit of measure)
          .Include(s => s.RObjekty)
              .ThenInclude(o => o.RSd)
                  .ThenInclude(sd => sd.RPol)
                      .ThenInclude(p => p.KMjNavigation)

          // Second path — loads measurements filtered by date + ZBV
          .Include(s => s.RObjekty)
              .ThenInclude(o => o.RSd)
                  .ThenInclude(sd => sd.RPol)
                      .ThenInclude(p => p.SSdPol
                          .Where(m =>
                              m.DatumMereni >= _od &&
                              m.DatumMereni <= _do))
                          .ThenInclude(sp => sp.KZbvNavigation)
                              .ThenInclude(z => z.ZbvPol)

          .FirstOrDefaultAsync();

      if (stav == null)
          throw new BadDataException("Stavba nenalezena");

      // Filter individual RPol items — one flag is always true
      // VyfiltrovatPolozkyZacinajiciNulou → exclude items whose Znacka starts with "0"
      // VyfiltrovatSDsNulouVeZnacce       → exclude items whose Znacka contains "0"
      // RSd with no surviving items is excluded from output by SetSD's RPol.Any() check
      foreach (var objekt in stav.RObjekty)
          foreach (var sd in objekt.RSd)
              sd.RPol = sd.RPol
                  .Where(p => req.VyfiltrovatPolozkyZacinajiciNulou
                      ? !p.Znacka.StartsWith("0")
                      : !p.Znacka.Contains("0"))
                  .ToList();

      data = new ReportMereniPolozekZaObdobiExcelData
      {
          Stavba = stav
      };
  }

  ---
  After GetData() completes

  - data.Stavba.RObjekty — all objekty of the stavba
  - Each objekt.RSd — all SDs, no Znacka filter at this level
  - Each sd.RPol — only položky that passed the RPol filter (Znacka does not start with "0" or does not contain "0", depending on which flag is active)
  - Each pol.KMjNavigation — measurement unit (always loaded)
  - Each pol.SSdPol — only measurements within the date range (or empty list if none)
  - Each SSdPol.KZbvNavigation.ZbvPol — ZBV data for those measurements

Root cause

  IKeyedServiceProvider is not registered in the .NET DI container — only IServiceProvider is auto-registered. The change in the PR commit replaced IServiceProvider with IKeyedServiceProvider, which breaks DI
   validation.

  The method GetRequiredKeyedService<T>(key) is an extension method on IServiceProvider (from ServiceProviderKeyedServiceExtensions), so IKeyedServiceProvider is not needed at all.

 Both GetHromadnyZaznamMereniDataHandlerWeb and GetDataProVymeruProvedenychPraciHandlerWeb have IKeyedServiceProvider in their constructor — change both to IServiceProvider. That's the entire fix.

Simple explanation

  The DI container is like a registry of services

  When the app starts, .NET registers all services into a container — a dictionary of "here's what I can provide when someone asks."

  IServiceProvider is automatically registered — it's the container itself. Any class can ask for it in its constructor and .NET will hand it over.

  IKeyedServiceProvider is a sub-interface of IServiceProvider (adds support for named/keyed lookups). But .NET does not register it separately. If a class asks for it in its constructor, .NET looks in the
  registry, finds nothing, and throws.

  ---
  The method confusion

  GetRequiredKeyedService<T>(key) — this is just an extension method sitting on top of IServiceProvider. Think of it like a helper function:

  // Defined as extension on IServiceProvider:
  public static T GetRequiredKeyedService<T>(this IServiceProvider sp, object key) { ... }

  So you call it on IServiceProvider — you never need IKeyedServiceProvider directly.

  ---
  What went wrong

  Someone thought: "I'm using keyed services, so I should inject the keyed version of the provider."

  That logic sounds reasonable but is wrong. The keyed lookup capability comes from the extension method, not from the type you inject. IServiceProvider is enough.

  Analogy: You don't need a "sports car driver's license" to press the sport mode button on a regular car. The regular license + the button is all you need.

  The core concept — inverted access table

  CUzivateleStavbyPristup is a deny table, not an access table. It stores who is blocked:

  User NOT in table → has access ✓
  User IN table     → denied ✗

  This is the opposite of what you might expect. The method HasAccess (line 88) makes it clear:

  public bool HasAccess(int userId)
  {
      return !CUzivateleStavbyPristup.Any(x => x.KUzivatel == userId);
      // "I have access if I am NOT in the deny list"
  }

  WPF analogy: imagine a blacklist — if your name is on it, you're out. If the list is empty, everyone is allowed in.

  ---
  Root Cause: Different DataContext = Different Hierarchy Level

  Both grids bind to the same property name OsobyZP, but on completely different model objects:

  ┌─────────────┬───────────────────┬────────────────────┬────────────────────────┬────────────────────────────────────────┐
  │    Grid     │       File        │  DataContext type  │      Entity level      │               Source API               │
  ├─────────────┼───────────────────┼────────────────────┼────────────────────────┼────────────────────────────────────────┤
  │ dgPodpisyZP │ ucStavbaNastaveni │ StavbyNastaveniDTO │ Stavba (site)          │ RozpocetDesktop_VratNastaveniStavby... │
  ├─────────────┼───────────────────┼────────────────────┼────────────────────────┼────────────────────────────────────────┤
  │ Podpisy     │ ucObjektDetail    │ ObjektDTO          │ Objekt (budget object) │ RozpocetDesktop_VratObjektAsync        │
  └─────────────┴───────────────────┴────────────────────┴────────────────────────┴────────────────────────────────────────┘

  They are reading different rows from the database — same PoziceVazby table, but filtered by TypUzlu and KodUzlu:

  - Stavba grid saves with KodUzlu = kodStavba (ucStavbaNastaveni.xaml.cs:2392)
  - Objekt grid saves with TypUzlu = TYP_UZLU.OBJEKT and KodUzlu = uloz.Kod (ucObjektDetail.xaml.cs:1173-1174)

  Why They Differ at Runtime

  The stavba-level OsobyZP are site-wide signatories set once in project settings. The objekt-level OsobyZP are per-object overrides — each ObjektDTO loads its own separate records from the API. Unless the backend explicitly
  copies the stavba records into each new objekt on creation, the objekt grid will be empty or have different values.

  There is a DefaultniPozice flag in the data (ucObjektDetail.xaml:1261 — IsReadOnly="{Binding DefaultniPoziceZP}"), which suggests "default positions" can be inherited/locked from the stavba level, but only if the backend
  populates them that way. The grid itself has no self-copying mechanism on the client side.

  In Short

  This is by design — they are not meant to be identical. The stavba grid shows site-level signatories; the objekt grid shows object-level signatories. If you expect them to match, the synchronization would have to happen on
  the server side (e.g., when creating/loading an objekt, the API should seed its OsobyZP from the stavba's OsobyZP). No such logic exists in the client code.

--------------
rule of thumb
--------------

The diagnostic output reveals the real problem: The S key event never reaches your Window_KeyDown handler!
What's Happening:

✅ You press Ctrl → Event fires (e.Key: LeftCtrl)
❌ You press S → No event fired at Window level!
👉 The NumericTextBox (or RozpocetSectionSeznam) is consuming the event before it bubbles up

Solution: Use PreviewKeyDown Instead
WPF has two keyboard event types:

PreviewKeyDown → Tunnels DOWN (Window → Child) - fires first
KeyDown → Bubbles UP (Child → Window) - fires last

The issue is binding update timing. When you press Ctrl+S:

PreviewKeyDown fires BEFORE the textbox commits its value
The control still has focus and hasn't triggered LostFocus
The binding hasn't updated yet
You're saving the old value from the binding

When you click the button:
Button click causes textbox to lose focus
LostFocus triggers binding update
Then the save happens with the new value

a classic WPF nested ScrollViewer + MouseWheel routing conflict

Correct design rule (key insight) :
Inner ScrollViewer should scroll first
Outer ListView should scroll only if inner cannot

The error is caused by this line being executed when the visual tree is NOT ready yet:

this.AddHandler(
    UIElement.MouseWheelEvent,
    new MouseWheelEventHandler(OnGlobalMouseWheel),
    handledEventsToo: true);


In WPF, calling AddHandler in a Window constructor before the visual tree is fully created can throw a NullReferenceException during build/XAML compilation, which Visual Studio reports as:

Unknown build error

This is a known WPF/XAML quirk, especially with:

code-behind event wiring

third-party controls

compiled XAML (.g.cs)

namespace proconom.Admin.GroupManager
public class GroupManagerContext : BaseObservableObject
        private void UpdatePermisionEntities() { PermissionEntities = GetPermisionEntities(UseUsers ? FetchUser : FetchGroup); }
        private TrueObservableCollection<BasePermissionEntity> GetPermisionEntities(Func<BasePermissionEntity, bool> filter)
        {
            if (OriginalPermissionEntities is null)
                return null;
            if (!OriginalPermissionEntities.Any())
                return new();
            return new(OriginalPermissionEntities.Where(filter));
        }
