Root cause

  IKeyedServiceProvider is not registered in the .NET DI container — only IServiceProvider is auto-registered. The change in the PR commit replaced IServiceProvider with IKeyedServiceProvider, which breaks DI
   validation.

  The method GetRequiredKeyedService<T>(key) is an extension method on IServiceProvider (from ServiceProviderKeyedServiceExtensions), so IKeyedServiceProvider is not needed at all.

 Both GetHromadnyZaznamMereniDataHandlerWeb and GetDataProVymeruProvedenychPraciHandlerWeb have IKeyedServiceProvider in their constructor — change both to IServiceProvider. That's the entire fix.

Simple explanation

  The DI container is like a registry of services

  When the app starts, .NET registers all services into a container — a dictionary of "here's what I can provide when someone asks."

  IServiceProvider is automatically registered — it's the container itself. Any class can ask for it in its constructor and .NET will hand it over.

  IKeyedServiceProvider is a sub-interface of IServiceProvider (adds support for named/keyed lookups). But .NET does not register it separately. If a class asks for it in its constructor, .NET looks in the
  registry, finds nothing, and throws.

  ---
  The method confusion

  GetRequiredKeyedService<T>(key) — this is just an extension method sitting on top of IServiceProvider. Think of it like a helper function:

  // Defined as extension on IServiceProvider:
  public static T GetRequiredKeyedService<T>(this IServiceProvider sp, object key) { ... }

  So you call it on IServiceProvider — you never need IKeyedServiceProvider directly.

  ---
  What went wrong

  Someone thought: "I'm using keyed services, so I should inject the keyed version of the provider."

  That logic sounds reasonable but is wrong. The keyed lookup capability comes from the extension method, not from the type you inject. IServiceProvider is enough.

  Analogy: You don't need a "sports car driver's license" to press the sport mode button on a regular car. The regular license + the button is all you need.

  ---
  Root Cause: Different DataContext = Different Hierarchy Level

  Both grids bind to the same property name OsobyZP, but on completely different model objects:

  ┌─────────────┬───────────────────┬────────────────────┬────────────────────────┬────────────────────────────────────────┐
  │    Grid     │       File        │  DataContext type  │      Entity level      │               Source API               │
  ├─────────────┼───────────────────┼────────────────────┼────────────────────────┼────────────────────────────────────────┤
  │ dgPodpisyZP │ ucStavbaNastaveni │ StavbyNastaveniDTO │ Stavba (site)          │ RozpocetDesktop_VratNastaveniStavby... │
  ├─────────────┼───────────────────┼────────────────────┼────────────────────────┼────────────────────────────────────────┤
  │ Podpisy     │ ucObjektDetail    │ ObjektDTO          │ Objekt (budget object) │ RozpocetDesktop_VratObjektAsync        │
  └─────────────┴───────────────────┴────────────────────┴────────────────────────┴────────────────────────────────────────┘

  They are reading different rows from the database — same PoziceVazby table, but filtered by TypUzlu and KodUzlu:

  - Stavba grid saves with KodUzlu = kodStavba (ucStavbaNastaveni.xaml.cs:2392)
  - Objekt grid saves with TypUzlu = TYP_UZLU.OBJEKT and KodUzlu = uloz.Kod (ucObjektDetail.xaml.cs:1173-1174)

  Why They Differ at Runtime

  The stavba-level OsobyZP are site-wide signatories set once in project settings. The objekt-level OsobyZP are per-object overrides — each ObjektDTO loads its own separate records from the API. Unless the backend explicitly
  copies the stavba records into each new objekt on creation, the objekt grid will be empty or have different values.

  There is a DefaultniPozice flag in the data (ucObjektDetail.xaml:1261 — IsReadOnly="{Binding DefaultniPoziceZP}"), which suggests "default positions" can be inherited/locked from the stavba level, but only if the backend
  populates them that way. The grid itself has no self-copying mechanism on the client side.

  In Short

  This is by design — they are not meant to be identical. The stavba grid shows site-level signatories; the objekt grid shows object-level signatories. If you expect them to match, the synchronization would have to happen on
  the server side (e.g., when creating/loading an objekt, the API should seed its OsobyZP from the stavba's OsobyZP). No such logic exists in the client code.

https://tfs-server.proconom.local/ProconomSW/PROCONOM/_workitems/edit/27322/
--------------
rule of thumb
--------------

The diagnostic output reveals the real problem: The S key event never reaches your Window_KeyDown handler!
What's Happening:

✅ You press Ctrl → Event fires (e.Key: LeftCtrl)
❌ You press S → No event fired at Window level!
👉 The NumericTextBox (or RozpocetSectionSeznam) is consuming the event before it bubbles up

Solution: Use PreviewKeyDown Instead
WPF has two keyboard event types:

PreviewKeyDown → Tunnels DOWN (Window → Child) - fires first
KeyDown → Bubbles UP (Child → Window) - fires last

The issue is binding update timing. When you press Ctrl+S:

PreviewKeyDown fires BEFORE the textbox commits its value
The control still has focus and hasn't triggered LostFocus
The binding hasn't updated yet
You're saving the old value from the binding

When you click the button:
Button click causes textbox to lose focus
LostFocus triggers binding update
Then the save happens with the new value

a classic WPF nested ScrollViewer + MouseWheel routing conflict

Correct design rule (key insight) :
Inner ScrollViewer should scroll first
Outer ListView should scroll only if inner cannot

The error is caused by this line being executed when the visual tree is NOT ready yet:

this.AddHandler(
    UIElement.MouseWheelEvent,
    new MouseWheelEventHandler(OnGlobalMouseWheel),
    handledEventsToo: true);


In WPF, calling AddHandler in a Window constructor before the visual tree is fully created can throw a NullReferenceException during build/XAML compilation, which Visual Studio reports as:

Unknown build error

This is a known WPF/XAML quirk, especially with:

code-behind event wiring

third-party controls

compiled XAML (.g.cs)
