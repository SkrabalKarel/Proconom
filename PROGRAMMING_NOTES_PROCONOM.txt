PDB problem
---------------------------

Debug → Windows → Modules** while debugging. Find your DLL, right-click → *Symbol Load Information*. It will tell you exactly which PDB paths it tried and why each failed — this is the definitive diagnostic, faster than guessing.



Breakpoint turning into a hollow circle ("The breakpoint will not currently be hit. No symbols have been loaded...") is almost always stale PDBs or a symbol mismatch, not a code problem. Clear them in this order — stop as soon as breakpoints work again.

**1. Close Visual Studio first.** Otherwise VS keeps PDBs locked and some deletes silently fail.

**2. Delete per-project `bin` and `obj` folders.**
From the solution root in PowerShell:
```powershell
Get-ChildItem -Include bin,obj -Recurse -Force | Remove-Item -Recurse -Force
```
This is the #1 cause in multi-project solutions like ProCONOM where one project references another's stale DLL+PDB pair.

**3. Delete the `.vs` folder** next to the `.sln`. It caches breakpoint bindings and IntelliSense state that can go out of sync with rebuilt PDBs.

**4. Clear the Visual Studio symbol cache.**
- `Tools → Options → Debugging → Symbols → Empty Symbol Cache`
- Default path: `%LOCALAPPDATA%\Temp\SymbolCache` — delete it manually if the button is greyed out.

**5. Clear the ComponentModelCache and MEF cache** (only if VS itself is misbehaving, not just breakpoints):
```
%LOCALAPPDATA%\Microsoft\VisualStudio\<version>\ComponentModelCache
```

**6. Rebuild (not just Build).** `Build → Rebuild Solution`. Build won't touch up-to-date projects, so a stale PDB survives.

### If breakpoints are still hollow after all of the above

Check these settings — they cause the exact same symptom but no amount of cleaning will fix them:

- **Configuration must be `Debug`**, not Release. Legacy solutions often have a custom config (`DebugInternal`, `DebugLocal`) where *some* projects are still set to Release — check `Build → Configuration Manager` project by project.
- **Project properties → Build → Advanced → Debugging Information = Portable or Full** (not `None` or `Embedded` if you're mixing).
- **Project properties → Build → Optimize code = OFF** for the project containing the breakpoint.
- **Tools → Options → Debugging → General:**
  - Uncheck *"Require source files to exactly match the original version"* (common culprit after git branch switch).
  - Uncheck *"Enable Just My Code"* temporarily to confirm symbols actually load.
- **Debug → Windows → Modules** while debugging. Find your DLL, right-click → *Symbol Load Information*. It will tell you exactly which PDB paths it tried and why each failed — this is the definitive diagnostic, faster than guessing.

### WPF-specific gotcha

If it's a WPF project and breakpoints in code-behind fail but XAML-generated `.g.cs` breakpoints work (or vice versa), delete `obj\Debug\<project>.g.cs` and the `.baml` files — the XAML compiler caches them and they get out of sync with the real PDB after partial builds. A Rebuild regenerates them.

### Nuclear option

```powershell
# From solution root, VS closed:
Remove-Item -Recurse -Force .vs
Get-ChildItem -Include bin,obj -Recurse -Force | Remove-Item -Recurse -Force
Remove-Item -Recurse -Force "$env:LOCALAPPDATA\Temp\SymbolCache"
```
Then reopen, Rebuild Solution, debug.

GIT-workflow when switching among branches
---------------------------

WIP Commit Workflow — Full Detail

  1. Creating a WIP commit

  You have uncommitted changes in branch1 and need to switch away.

  In Visual Studio — Git Changes panel:
  1. Stage all files (click + next to each file, or + next to "Changes" to stage all)
  2. Type a message: WIP: implementing X
  3. Click Commit Staged

  Now branch1 has a WIP commit. You can freely switch to branch2.

  ---
  2. Coming back and continuing work

  Switch back to branch1. Your WIP commit is there. Just edit files normally. Now you have:
  - The WIP commit (already committed)
  - New uncommitted changes on top of it

  ---
  3. Adding more changes into the WIP commit (Amend)

  When you want to fold new changes INTO the existing WIP commit (not create a second commit):

  In Visual Studio:
  1. Stage the new changes
  2. Check the Amend checkbox (below the commit message box)
  3. Keep the same message or update it
  4. Click Commit Staged

  The previous WIP commit is replaced with a new one that includes everything. From Git's point of view, the old commit never existed — it is rewritten locally.

  ⚠ Only amend commits that have NOT been pushed to remote yet. Amending a pushed commit rewrites history and causes problems for anyone else on the branch.

  ---
  4. Reverting changes before final push

  You have options depending on what you want to undo:

  A — Discard specific uncommitted file changes (not yet staged/committed)
  - Git Changes panel → right-click file → Discard Changes
  - File goes back to the state of the last commit

  B — Unstage a file (staged but not committed yet)
  - Git Changes panel → click − next to the staged file
  - File moves back to unstaged, changes preserved

  C — Undo the entire WIP commit but keep the changes as uncommitted
  - Git menu → View Branch History
  - Right-click the WIP commit → Reset → Mixed (Keep Changes)
  - The commit disappears, all changes come back as unstaged edits
  - You can now selectively stage and recommit only what you want

  D — Undo the entire WIP commit AND discard all changes (nuclear)
  - Git menu → View Branch History
  - Right-click the WIP commit → Reset → Hard (Delete Changes)
  - ⚠ This permanently deletes all changes in that commit — no undo

  ---
  5. Preparing the final "real" commit before push

  When you're done with the feature:

  1. If you still have WIP commits: use Reset → Mixed (option C above) to uncommit everything
  2. Review all changes carefully
  3. Stage only what belongs together (you can stage file-by-file or even hunk-by-hunk in VS via the diff view)
  4. Write a proper commit message
  5. Commit → then Push

  Or alternatively: just Amend the WIP commit with the final message — skips the reset step entirely.

  Architectural Pattern

  HTTP Request
       │
       ▼
  [Controller]              ← thin layer, only routing + auth
       │  ResolveResponse(request)
       ▼
  [GeneralController]       ← base class, sends via MediatR, centralizes exception → HTTP mapping
       │  _mediator.Send(request)
       ▼
  [IRequestHandler<TRequest, TResponse>]   ← all business logic lives here
       │
       ▼
  [DbContext / Services / Factories / Azure / Firebase / ...]

  Key points:
  - Controllers contain zero business logic — one-liners calling await ResolveResponse(request)
  - GeneralController (Commons/GeneralController.cs) maps all domain exceptions to HTTP responses automatically:
    - NoDataFoundException → 404
    - BadDataException → 400
    - ForbiddenException → 403
    - ConcurrencyException → 409
    - NoContentOkException → 204
    - etc.
  - Each operation (GetToDos, AddToDo, UpdateToDo…) is its own Handler class with co-located Request + Response + DTO

  How to Add a New Endpoint — Step by Step

  This follows MODE 2 (new feature) from the project rules. The pattern is always the same, regardless of domain.

  Step 1 — Create the Handler file

  Location: v1/Modules/YourModule/Handlers/GetSomethingHandler.cs

  The file holds three classes together: handler, request, response.

  using EFModels.Models;
  using MediatR;

  namespace TestApi.v1.Modules.YourModule.Handlers
  {
      // ── Handler ──────────────────────────────────────────────────────────
      public class GetSomethingHandler : IRequestHandler<GetSomethingRequest, GetSomethingResponse>
      {
          private readonly DB_DevelopContext _ctx;
          private readonly IClaimResolver _claimResolver;

          public GetSomethingHandler(DB_DevelopContext ctx, IClaimResolver claimResolver)
          {
              _ctx = ctx;
              _claimResolver = claimResolver;
          }

          public async Task<GetSomethingResponse> Handle(GetSomethingRequest request, CancellationToken cancellationToken)
          {
              int userId = _claimResolver.ResolveInt(System.Security.Claims.ClaimTypes.NameIdentifier);

              var data = await _ctx.YourTable
                  .Where(x => x.XId == request.Id)
                  .Select(x => new SomethingDTO { Id = x.XId, Name = x.Nazev })
                  .FirstOrDefaultAsync(cancellationToken);

              if (data == null)
                  throw new NoDataFoundException();

              return new GetSomethingResponse { Data = data };
          }
      }

      // ── Request ──────────────────────────────────────────────────────────
      public class GetSomethingRequest : IRequest<GetSomethingResponse>
      {
          public int Id { get; set; }
      }

      // ── Response ─────────────────────────────────────────────────────────
      public class GetSomethingResponse
      {
          public SomethingDTO Data { get; set; }
      }

      // ── DTO ──────────────────────────────────────────────────────────────
      public class SomethingDTO
      {
          public int Id { get; set; }
          public string Name { get; set; }
      }
  }

  Step 2 — Add the endpoint to the Controller

  Location: v1/Modules/YourModule/YourModuleController.cs

  [Route("api/[controller]")]
  [ApiController]
  [Authorize(Roles = Role.V1User)]
  public class YourModuleController : GeneralController
  {
      public YourModuleController(IServiceProvider serviceProvider) : base(serviceProvider) { }

      [HttpGet("{Id}")]
      public async Task<ActionResult<GetSomethingResponse>> GetSomething([FromRoute] GetSomethingRequest request)
          => await ResolveResponse(request);

      [HttpPost]
      public async Task<ActionResult<CreateSomethingResponse>> CreateSomething([FromBody] CreateSomethingRequest request)
          => await ResolveResponse(request);
  }

  That's it for the controller. One line per endpoint.

  Step 3 — Register services if needed

  If your handler needs a new service (not already registered), add it to Startup.cs → ConfigureServices:

  services.AddScoped<IYourNewService, YourNewService>();

  MediatR handlers are auto-discovered — no registration needed as long as they're in the same assembly.

  Step 4 — No additional wiring needed

  - MediatR picks up handlers automatically via services.AddMediatR(typeof(Startup).Assembly, ...)
  - GeneralController.ResolveResponse() handles all HTTP status mapping automatically
  - Authentication/authorization is enforced by the [Authorize] attribute on the controller class or individual action

  ---
  Key Rules to Remember

  - Never put logic in the controller — controllers are pure routing
  - Exception → HTTP mapping is centralized in GeneralController — throw domain exceptions from handlers, not return BadRequest(...)
  - All DbContext operations must be async — .FirstOrDefaultAsync(), .ToListAsync(), never .FirstOrDefault() on EF queries
  - Claims-based user resolution via IClaimResolver — never trust request body for user identity
  - DB_DevelopContext = project/construction data, DB_MasterContext = tenant/user/database registry

# WPF — TextChanged Re-entrancy Bug
-------------------------
## What it is
When you modify `TextBox.Text` programmatically inside a `TextChanged` handler,
WPF fires `TextChanged` **again synchronously** before the first call returns.
This causes infinite loops, repeated dialogs, or other unintended side effects.
## When it happens
Any `TextChanged` handler that:
- truncates the text (`textBox.Text = textBox.Text.Remove(...)`)
- replaces or transforms the text in any way
## Symptom
- A message dialog appears repeatedly / in a loop on every keystroke past the limit
- Or the handler visibly fires more times than expected
## Solution
Unsubscribe the handler **before** modifying `Text`, resubscribe **after**:

```csharp
private void tbName_TextChanged(object sender, TextChangedEventArgs e)
{
    if (sender is not TextBox textBox || textBox.Text.Length < 200)
        return;

    textBox.TextChanged -= tbName_TextChanged;  // prevent re-entrancy

    MessageWindow.Dialog.Show(Properties.Resources.msgNazevNesmiMitPres200Znaku);
    textBox.Text = textBox.Text.Remove(textBox.Text.Length - 1);
    textBox.Select(textBox.Text.Length, 0);

    textBox.TextChanged += tbName_TextChanged;  // restore
}
```

## Key rule
> In WPF, **any assignment to a dependency property inside its own change handler
> will re-trigger that handler**. Always guard with unsubscribe/resubscribe or a
> boolean flag before mutating the source property.
## Applies to
`TextChanged`, `SelectionChanged`, `ValueChanged`, and similar WPF change events
where the handler modifies the very property being observed.

A true MVVM approach would separate UI logic into ViewModels and minimize code-behind, using commands and property bindings. Here, business logic and UI logic are mixed in the UserControl, which is more typical of a traditional WPF application without a formal architectural pattern.
Used correctly, ChatGPT becomes your architectural brain, and Copilot becomes your fast hands.

proconom project is a classic WPF code-behind approach, with some MVVM elements but not a full implementation

7. How to Move Toward MVVM
•	Create ViewModel classes for each View/UserControl.
•	Move logic (data loading, API calls, state management) from code-behind to ViewModel.
•	Expose properties and collections via ViewModel, implementing INotifyPropertyChanged.
•	Use Commands (ICommand) for user actions instead of event handlers.
•	Bind UI elements to ViewModel properties and commands.
•	Inject ViewModel into View via DataContext.
---
8. Why MVVM Matters
•	Testability: ViewModels can be unit tested.
•	Maintainability: Separation of concerns makes code easier to manage.
•	Scalability: Easier to add features and refactor.

You need three things:
A flag that tracks whether anything changed (IsDirty)
Set this flag to true whenever user changes data
Before closing / navigating / switching context:

If user chooses Yes → Save
No → Discard
Cancel → Abort action
